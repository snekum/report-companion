# Report Companion

Turn a confusing medical document into an organised, understandable record—with every extracted fact linked to its source.

A portfolio prototype with three parts:

1. **A document workspace** (React + TypeScript + Vite, static, GitHub Pages ready). Open a document, see the extracted facts next to the original, click a fact to highlight the line it came from, fix mistakes, compare two reports, save questions and export an appointment brief.
2. **A fine-tuned small model.** Qwen3-1.7B with a QLoRA adapter trained to turn a short document into a fixed set of fields, each with a quote copied from the document.
3. **An honest comparison** of the fine-tuned model with the original model and with a plain rule-based extractor, on synthetic test documents and a hand-written challenge set.

It runs in the browser: the model runs on the visitor's own GPU through WebLLM, so documents never leave the device and hosting costs nothing beyond static files.

**This is a document-understanding prototype, not a diagnostic tool.** All example patients are fictional (generated by Synthea). Results on synthetic documents say little about real clinical records.

## Status (November 2026): work in progress

What works:

- **The fine-tuned model, run in Python.** On 204 test documents it scores an overall F1 of 0.99, against 0.82 for the original model. On 20 hand-written documents built to trip it up, it scores 0.93 against 0.61. (F1 combines how many of the facts it found with how many of the facts it gave were right; 1.0 is perfect.) Full tables are in [results/RESULTS.md](results/RESULTS.md).
- **The app.** It runs the original model live in your browser and shows the fine-tuned model's answers as prepared results, from the earlier pilot run.

What doesn't work yet:

- **The fine-tuned model inside the browser.** The browser version stores the weights at 4-bit precision, and that rounding undoes most of the fine-tuning: only 10% of its answers come out in a valid format, against 100% in Python on the same 40 documents. The cause is that training rounded the base model one way and the browser rounds it another. The step-by-step investigation is in [results/deployment/diag_browser/](results/deployment/diag_browser/) and [PROGRESS.md](PROGRESS.md). A retrain on a base rounded exactly the way the browser rounds it is under way.

## Reproduce it

Commands are for Git Bash on Windows; on Linux/macOS use `.venv-*/bin/python`.

### 1. Data (CPU, ~5 minutes)

```bash
bash tools/fetch_tools.sh                 # Temurin 21 JRE + Synthea v4.0.0 (checksummed) into tools/
bash pipeline/run_synthea.sh              # 700 synthetic patients, fixed seeds and reference date
python -I pipeline/load_synthea.py        # CSV + FHIR -> data/interim/records.json
python -I pipeline/build_dataset.py       # split by patient, render, check labels -> data/processed/
python -I pipeline/challenge/challenge_set.py
python -I pipeline/build_demo.py          # the three example journeys (demo-split patients only)
```

### 2. Baseline and evaluation (CPU)

```bash
python -I model/baseline_regex.py --split test
python -I model/evaluate.py --pred results/predictions/regex_test.jsonl --split test --sections document_date,labs
python -I model/test_common.py            # shared validation cases
```

### 3. Models (NVIDIA GPU)

```bash
uv venv --python 3.12 .venv-train
uv pip install -p .venv-train/Scripts/python.exe torch==2.9.1 --index-url https://download.pytorch.org/whl/cu126
uv pip install -p .venv-train/Scripts/python.exe -r model/requirements.txt

# original model
.venv-train/Scripts/python.exe model/generate.py --split test --tag base --batch-size 8
# fine-tune (pilot, then the real run)
.venv-train/Scripts/python.exe model/train.py --run pilot --n-train 160 --epochs 1
.venv-train/Scripts/python.exe model/train.py --run final --n-train 951 --epochs 1
.venv-train/Scripts/python.exe model/generate.py --split test --tag ft-final --adapter model/outputs/final/adapter --batch-size 8
python -I model/evaluate.py --pred results/predictions/ft-final_test.jsonl --split test
python -I model/summarize.py --ft-tag ft-final --train-run final
```

On a 4 GB GTX 1650 training takes ~32 s per example, so the full run is better done on a free cloud T4: run `bash tools/make_cloud_bundle.sh`, then open `model/cloud_train_eval.ipynb` on Kaggle or Colab (instructions inside), and unzip the returned `outputs.zip` at the repository root.

### 4. Browser model (Docker Desktop for the conversion)

```bash
.venv-train/Scripts/python.exe model/merge_adapter.py --adapter model/outputs/final/adapter --out model/merged/final
bash model/convert_mlc.sh model/merged/final ReportCompanion-Qwen3-1.7B-q4f16_1-MLC
```

The converted folder (~1 GB) is what gets hosted for the app (for example as a Hugging Face model repo). Nothing is uploaded by these scripts.

### 5. App

```bash
cd app
npm ci
npm test                 # unit tests, incl. Python/TypeScript parity (on Windows, cd via "D:/..." not "d:/...": vitest loads itself twice if the drive letter case differs)
npm run dev              # http://localhost:5199
node scripts/verify-ui.mjs                       # browser checks + screenshots
node scripts/verify-webgpu.mjs original          # loads the original model in Chrome via WebGPU
npm run build            # static site in app/dist, works from any subpath
```

To try a locally converted fine-tuned model: `node scripts/serve-model.mjs` and start the dev server with `VITE_FINETUNED_MODEL_URL=http://localhost:5300/ReportCompanion-Qwen3-1.7B-q4f16_1-MLC`.
