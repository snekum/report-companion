# Report Companion

Turn a confusing medical document into an organised, understandable record—with every extracted fact linked to its source.

An independent prototype exploring an approach for MedARC's [AMFV (Agentic Medical Fact Verifier)](https://github.com/MedARC-AI/amfv) project. It isn't an official MedARC project and isn't used by them. AMFV breaks text into individual medical claims and checks each one against evidence. This prototype tries a related idea on medical records: a small model splits a document into individual facts, each with the exact line it came from, and plain code checks every fact against the document before it's shown.

It has three parts:

1. **A document workspace** (React + TypeScript + Vite, static, GitHub Pages ready). Open a document, see the extracted facts next to the original, click a fact to highlight the line it came from, fix mistakes, compare two reports, save questions and export an appointment brief.
2. **A fine-tuned small model.** Qwen3-1.7B with a LoRA adapter (a small add-on trained on top of frozen weights) trained to turn a short document into a fixed set of fields, each with a quote copied from the document.
3. **An honest comparison** of the fine-tuned model with the original model and with a plain rule-based extractor, on synthetic test documents and a hand-written challenge set.

It runs in the browser: the model runs on the visitor's own GPU through WebLLM, so documents never leave the device and hosting costs nothing beyond static files.

**This is a document-understanding prototype, not a diagnostic tool.** All example patients are fictional (generated by Synthea). Results on synthetic documents say little about real clinical records.

## Results (November 2026)

F1 below combines how many of the facts a model found with how many of the facts it gave were right; 1.0 is perfect.

| | Original model | Fine-tuned model |
|---|---|---|
| Test set, 204 synthetic documents: all facts F1 | 0.82 | 0.99 |
| Test set: answers in the required format | 22% | 96% |
| Test set: facts not found in the document | 52 | 0 |
| Challenge set, 20 hand-written tricky documents: all facts F1 | 0.61 | 0.86 |

The fine-tuned model also runs in Chrome. On 40 test documents it gives the same scores there as in Python (all facts F1 0.996), at about 32 seconds per document on a laptop GTX 1650.

Getting it into the browser took a second training run. The browser stores weights in 4 bits, using its own rounding. The first fine-tune was trained on weights rounded a different way, and after conversion it fell apart: only 10% of its browser answers were in a valid format. The fix was to train on weights rounded exactly the way the browser rounds them ([model/q4grid.py](model/q4grid.py)). That model works in the browser. It costs some accuracy on the hand-written challenge set: 0.86 against 0.93 for the first fine-tune, which can't run in the browser. The investigation is in [results/deployment/diag_browser/](results/deployment/diag_browser/) and [PROGRESS.md](PROGRESS.md).

Full tables, including both fine-tunes and both roundings of the original model: [results/RESULTS.md](results/RESULTS.md).

**State of the app:** it runs the original model live in your browser. The fine-tuned model's answers are shown as prepared results, because its converted weights (about 1 GB) aren't hosted yet.

## Reproduce it

Commands are for Git Bash on Windows; on Linux/macOS use `.venv-*/bin/python`.

### 1. Data (CPU, ~5 minutes)

```bash
bash tools/fetch_tools.sh                 # Temurin 21 JRE + Synthea v4.0.0 (checksummed) into tools/
bash pipeline/run_synthea.sh              # 700 synthetic patients, fixed seeds and reference date
python -I pipeline/load_synthea.py        # CSV + FHIR -> data/interim/records.json
python -I pipeline/build_dataset.py       # split by patient, render, check labels -> data/processed/
python -I pipeline/challenge/challenge_set.py
python -I pipeline/build_demo.py          # the three example journeys (demo-split patients only)
```

### 2. Baseline and evaluation (CPU)

```bash
python -I model/baseline_regex.py --split test
python -I model/evaluate.py --pred results/predictions/regex_test.jsonl --split test --sections document_date,labs
python -I model/test_common.py            # shared validation cases
```

### 3. Models (NVIDIA GPU)

```bash
uv venv --python 3.12 .venv-train
uv pip install -p .venv-train/Scripts/python.exe torch==2.9.1 --index-url https://download.pytorch.org/whl/cu126
uv pip install -p .venv-train/Scripts/python.exe -r model/requirements.txt

# original model
.venv-train/Scripts/python.exe model/generate.py --split test --tag base --batch-size 8
# fine-tune on weights rounded the way the browser rounds them (the shipped model)
.venv-train/Scripts/python.exe model/train.py --run q4grid --n-train 951 --epochs 1 --base-grid q4f16_1
.venv-train/Scripts/python.exe model/generate.py --split test --tag ft-q4grid --adapter model/outputs/q4grid/adapter --base-grid q4f16_1 --batch-size 8
python -I model/evaluate.py --pred results/predictions/ft-q4grid_test.jsonl --split test
bash tools/make_results.sh                # results/RESULTS.md + summary.json
```

The earlier fine-tune (`final`, trained on nf4 weights, broken in the browser) is the same commands without `--base-grid`. On a 4 GB GTX 1650 training takes ~32 s per example, so the full run is better done on a free cloud T4: run `bash tools/make_cloud_bundle.sh` and `python -I tools/make_cloud_notebook.py model/cloud_train_eval.ipynb`, then open the notebook on Kaggle or Colab (instructions inside), and unzip the returned `outputs.zip` at the repository root.

### 4. Browser model (Docker Desktop for the conversion)

```bash
.venv-train/Scripts/python.exe model/merge_adapter.py --adapter model/outputs/q4grid/adapter --out model/merged/q4grid
bash model/convert_mlc.sh model/merged/q4grid ReportCompanion-q4grid-Qwen3-1.7B-q4f16_1-MLC
.venv-train/Scripts/python.exe results/deployment/diag_browser/mlc_q4grid_check.py   # unpack the browser weights, check them in Python
```

The converted folder (~1 GB) is what gets hosted for the app (for example as a Hugging Face model repo). Nothing is uploaded by these scripts.

### 5. App

```bash
cd app
npm ci
npm test                 # unit tests, incl. Python/TypeScript parity (on Windows, cd via "D:/..." not "d:/...": vitest loads itself twice if the drive letter case differs)
npm run dev              # http://localhost:5199
node scripts/verify-ui.mjs                       # browser checks + screenshots
node scripts/verify-webgpu.mjs original          # loads the original model in Chrome via WebGPU
npm run build            # static site in app/dist, works from any subpath
```

To try a locally converted fine-tuned model: `node scripts/serve-model.mjs` and start the dev server with `VITE_FINETUNED_MODEL_URL=http://localhost:5300/ReportCompanion-q4grid-Qwen3-1.7B-q4f16_1-MLC`. The browser scores came from `node scripts/browser-eval.mjs finetuned ../data/processed/test40.jsonl ../results/predictions/ft-q4grid-browser_test40.jsonl http://localhost:5300/ReportCompanion-q4grid-Qwen3-1.7B-q4f16_1-MLC`.
